# 拾光同频第一周 Demo 分工与协作方案

## 1. 第一周总体目标

第一周不追求实现完整产品，目标是交付一个能够稳定演示的最小可行版本。Demo 需要打通以下业务链路：

1. 用户使用账号登录小程序。
2. 用户发布一条包含文字、单张图片、标签、心情和校园地点的时光印记。
3. 首页能够展示已发布的印记。
4. 用户能够查看印记详情，并按照关键词或标签搜索内容。
5. 其他用户能够对印记发表评论。
6. 管理员能够登录 Web 后台，查看用户和内容，并下架指定内容。

本周应保证小程序、后端、数据库和 Web 管理后台真实连通。页面可以简洁，但核心流程不能只使用静态页面或模拟数据。

## 2. 第一周功能范围

### 2.1 必须完成

- 普通用户登录与退出。
- 小程序登录状态保存。
- 发布文字和单张图片印记。
- 为印记选择标签、心情和校园地点。
- 首页印记列表与印记详情。
- 按关键词或标签查询印记。
- 发表评论和查看评论。
- 管理员登录。
- 后台用户列表和内容列表。
- 管理员下架内容。
- 基础权限控制和统一错误提示。
- 初始化演示账号和演示数据。

### 2.2 可以简化

- 第一周使用普通账号密码登录，暂不接入微信授权登录。
- 图片只支持单张上传，不做多图编辑。
- 标签、心情和地点使用预设选项。
- 搜索只实现关键词和单个标签筛选。
- 管理后台统计只显示用户总数、内容总数和评论总数。
- Agent 只保留入口或交互原型，不作为主链路的必需功能。

### 2.3 暂不实现

- 视频上传和视频摘要。
- 完整好友系统、即时聊天和校园搭子。
- 圈子管理、双人时光线和时光共振。
- 时光胶囊、故事集和年度报告。
- 复杂同频度算法和大模型推荐。
- 真实地图定位。
- 完整举报审核和智能安全 Agent。

## 5. 协调人开工前应创建的内容

建议先创建一个独立项目仓库，不要直接把代码混放在课程实验文件目录中。仓库可以采用以下结构：

```text
shiguang-tongpin/
├─ miniprogram/              # 微信小程序
├─ admin-web/                # Vue 3 管理后台
├─ backend/                  # Spring Boot 后端
├─ database/
│  ├─ schema.sql             # 建表脚本
│  └─ seed.sql               # 演示账号和演示数据
├─ docs/
│  ├─ requirements.md        # 第一周功能范围与验收标准
│  ├─ api.md                 # 接口文档
│  ├─ database.md            # 表结构和字段说明
│  ├─ tasks.md               # 任务负责人和状态
│  ├─ bugs.md                # 缺陷记录
│  └─ demo-script.md         # 最终演示脚本
├─ .env.example              # 环境变量示例，不保存真实密码
├─ .gitignore
└─ README.md                 # 项目启动和协作说明
```

### 5.1 最先创建的文件

#### README.md

至少写明：

- 项目简介和本周 Demo 范围。
- 前后端使用的技术栈。
- 环境要求。
- 数据库初始化方法。
- 小程序、后端和管理后台的启动方式。
- 演示账号。
- 常见启动问题。

#### docs/requirements.md

只记录本周必须完成和明确不做的功能。任何新需求先写入后续待办，不能直接加入本周开发。

#### docs/api.md

每个接口至少包含：

- 接口名称和负责人。
- 请求方法与路径。
- 是否需要登录及所需角色。
- 请求参数示例。
- 成功响应示例。
- 常见错误码。
- 当前状态：待设计、开发中、可联调或已验收。

前端不能只通过聊天记录确认字段，应以该文件中的接口定义为准。

#### database/schema.sql

第一周建议先确定以下核心表：

- `user`：普通用户和管理员账号。
- `post`：时光印记主体。
- `post_media`：印记图片。
- `tag`：标签。
- `post_tag`：印记与标签关联。
- `comment`：评论。

心情和地点可以先作为 `post` 表中的枚举字段，降低第一周开发复杂度。

#### database/seed.sql

至少准备：

- 一个管理员账号。
- 两个普通用户账号。
- 若干标签。
- 三至五条不同标签、心情和地点的印记。
- 两至三条评论。

固定演示数据能够减少现场临时录入和空页面风险。

#### .env.example

只保存变量名称和示例值，例如数据库地址、数据库用户名、上传目录和接口地址。不要提交真实密码、密钥或个人 Token。

## 6. Git 协作方式

### 6.1 分支建议

- `main`：只保存能够稳定演示的版本。
- `develop`：本周集成分支。
- `feature/模块名-姓名缩写`：个人功能分支。
- `fix/问题名称-姓名缩写`：缺陷修复分支。

示例：

```text
feature/auth-lzh
feature/post-jkn
feature/search-cax
feature/admin-zl
```

不要让八个人直接向 `main` 提交代码。功能完成后先合并到 `develop`，通过测试后再将稳定版本合并到 `main`。

### 6.2 提交要求

- 一次提交只完成一个明确任务。
- 提交信息写清模块和动作，例如 `feat(post): add post creation api`。
- 不提交编译产物、依赖目录、IDE 配置、真实密码和上传测试文件。
- 修改公共接口或数据库字段时，必须同步更新 `docs/api.md` 或 `database/schema.sql`。
- 合并前至少由另一名相关成员检查代码和接口影响。

## 7. 推荐的协调方式

### 7.1 先冻结范围，再开始编码

所有成员先确认本文件中的“必须完成、可以简化、暂不实现”。对本周主链路没有帮助的新想法统一记录到后续待办，不立即开发。

### 7.2 先定数据和接口，再分别开发页面

页面负责人和接口负责人在编码前确认字段名称、类型和示例。接口文档确认后，小程序和后台可以先使用相同结构的模拟数据开发，后端完成后再切换为真实请求。

### 7.3 按完整功能验收，不按代码数量验收

“页面已画完”或“接口已写完”都不能单独算完成。任务完成应同时满足：

- 页面能够操作。
- 请求能够到达真实后端。
- 数据能够写入或读取数据库。
- 异常情况有提示。
- 相关测试通过。
- 文档与实际接口一致。

### 7.4 依赖问题及时公开

成员遇到阻塞时，应说明：

- 当前正在完成什么任务。
- 被哪个接口、字段或环境问题阻塞。
- 需要谁提供什么内容。
- 是否存在不依赖该问题的其他工作。

不要等到准备合并时才报告接口不一致或环境无法启动。

### 7.5 由协调人维护唯一事实来源

建议将以下内容作为团队唯一依据：

- 功能范围以 `docs/requirements.md` 为准。
- 接口字段以 `docs/api.md` 为准。
- 数据库结构以 `database/schema.sql` 为准。
- 任务状态以 `docs/tasks.md` 或统一任务看板为准。
- 演示步骤以 `docs/demo-script.md` 为准。

聊天信息只用于讨论，最终结论必须更新到对应文件，避免不同成员记住不同版本。

## 8. 第一周完成标准

满足以下条件后，第一周 Demo 才算完成：

- 新环境可以按照 README 启动后端、管理后台和小程序。
- 数据库脚本可以完整执行。
- 普通用户和管理员账号均可登录。
- 用户能够发布并查看一条带图片、标签、心情和地点的印记。
- 用户能够搜索内容并发表评论。
- 管理员能够查看并下架内容。
- 下架后的内容不会继续出现在小程序公开列表中。
- 核心接口测试通过，没有阻断演示的严重缺陷。
- 演示数据、演示账号和演示脚本准备完毕。
- `main` 分支保存经过验收的稳定版本。

## 9. 协调人建议执行顺序

作为项目协调人，建议先完成以下工作，再让所有成员全面编码：

1. 创建独立 Git 仓库和基础目录。
2. 创建 `README.md`、`.gitignore` 和 `.env.example`。
3. 将本周范围写入 `docs/requirements.md`。
4. 将人员任务写入 `docs/tasks.md` 或任务看板。
5. 组织后端和各模块负责人确定核心表结构，将结果写入 `database/schema.sql`。
6. 确定接口路径和请求响应格式，将结果写入 `docs/api.md`。
7. 创建 `main`、`develop` 和个人功能分支。
8. 各成员按模块开发并向 `develop` 提交合并请求。
9. 持续更新任务状态、接口变更和缺陷记录。
10. 主链路通过验收后，再合并到 `main` 并按 `docs/demo-script.md` 演示。

你不需要提前替所有人创建业务代码文件。最重要的是先创建仓库骨架、范围文档、接口文档、数据库脚本位置和任务表，然后由每个负责人在自己的模块目录中创建代码。这样既能统一规范，也能保留清晰的个人代码贡献记录。
